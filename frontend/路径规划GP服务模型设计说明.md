# 路径规划 GP 服务模型设计说明

> 文档版本：v1.0  

---

## 一、业务需求理解摘要

### 1.1 三个场景的输入输出差异

| 维度 | 场景一：导航到问题树 | 场景二：拍照机位路线 | 场景三：季节主题路线 |
| --- | --- | --- | --- |
| 使用者 | 巡检人员 / 养护人员 | 游客 | 游客 |
| 触发方式 | 工单详情点击“去复核”/“去处置” | 自主选择机位点后点击“开始导航” | 选择观赏窗口后点击“开始导航” |
| 起点 | 当前定位（实时，每次不同） | 当前定位（实时） | 当前定位（实时） |
| 途经点 | 无 | 游客自选，可空，数量不固定 | 后端按观赏窗口预设，固定一组 |
| 终点 | 工单关联树木坐标（固定） | 游客指定（必选） | 观赏窗口预设终点（固定） |
| 规划原则 | 单一起点到单一终点的最短路径 | 经过全部指定途经点、到达终点的最短总路径 | 经过全部预设途经点、到达终点的最短总路径 |
| 途经点顺序 | 不适用 | 自动顺序优化（TSP 式） | 与场景二保持一致，自动顺序优化 |
| 前端展示 | 步行距离、预计步行时间 | 步行距离、预计步行时间 | 步行距离、预计步行时间 |
| 园区判定 | 终点所属园区决定，无需缓冲区判定 | 定位所在园区路网缓冲区决定可选机位点 | 定位所在园区路网缓冲区决定可选观赏窗口 |

三个场景的共性：起点都是实时定位，终点坐标固定或预设，最终都输出路径几何、总距离和预计步行时间。差异集中在“途经点是否存在、途经点来源、是否参与自动排序”。

### 1.2 园区路网缓冲区判定机制的理解

- 缓冲区是以两个园区各自的路网数据（用于构建网络数据集的同一份道路中心线）做 Buffer 运算生成。
- 缓冲区用于回答一个布尔问题：用户当前定位是否落在某个园区的路网影响范围内，从而决定向游客展示哪个园区的机位点 / 观赏窗口。
- 判定逻辑放在前端本地：前端预加载两个园区的缓冲区范围数据，拿到定位后本地做点位判定；后端不为此提供实时计算服务。
- 场景一不需要该判定：终点树坐标已确定园区，且起点允许在园区外（如养护人员从园区外赶来），直接按工单携带的园区标识规划即可。

### 1.3 途经点自动顺序优化的确认方案

- 场景二、场景三统一使用 Route 求解器的“查找最佳顺序”（Find Best Order / Reorder Stops to Find Optimal Route）模式，即 TSP 式自动排序。
- 建议在求解器中启用“保留第一个停靠点”与“保留最后一个停靠点”：起点固定为路径首点、终点固定为路径末点，仅中间途经点参与自动最优排序。这与“从起点出发、经过全部途经点、到达终点”的业务语义一致。
- 求解完成后，模型通过输出停靠点结果的 `StopSequence` 字段得到实际经过顺序，并携带前端传入的 `stop_id` 属性返回，确保顺序与途经点标识一一对应。

以上理解与需求描述一致，文档按此展开。

## 二、总体方案与职责边界

### 2.1 总体技术路线

1. 数据准备阶段：两园区路网数据导入 FileGDB，构建各自独立的网络数据集；同一阶段离线生成园区路网缓冲区要素类与若干配置表。
2. 模型构建阶段：在 ModelBuilder 中搭建一个通用路径规划工具，模型环境输出坐标系配置为 EPSG:4490。
3. 服务发布阶段：桌面端调试无误后，将模型共享发布为 GP 地理处理服务，部署至 GeoScene Server。
4. 前端调用阶段：前端完成定位、坐标系归一、园区缓冲区判定与园区内数据过滤后，调用 GP 服务获取路径几何、距离、时间与途经点实际顺序。

### 2.2 职责分界（重要）

| 环节 | 归属方 | 说明 |
| --- | --- | --- |
| 定位获取与坐标源纠偏 | 前端 | 前端知道定位来源是浏览器 GPS、高德 SDK 还是天地图，负责统一为 CGCS2000 经纬度（EPSG:4490） |
| 园区路网缓冲区判定 | 前端（v1） | 判断定位是否落在某园区路网缓冲区内，产出 `park_id` |
| 机位点 / 观赏窗口园区归属过滤 | 前端 + 业务数据接口 | 只展示当前所在园区的选项 |
| 纯路径计算 | GP 服务 | 接收已确定的园区标识、起点、终点、可选途经点，做最短路径与自动排序 |


GP 服务内部**不重复做缓冲区判定**，只校验园区参数值并按参数选择网络数据集。后端负责人不要把“用户是否在园区内”“该推荐哪些机位点”等逻辑混入 GP 模型。

## 三、园区路网缓冲区判定机制设计

### 3.1 缓冲区数据生成方式

**推荐方案：离线预生成，与网络数据集构建在同一数据准备阶段完成。**

生成方式：

- 输入要素：与构建网络数据集完全一致的园区道路中心线要素类（大兴善寺一份、唐大慈恩寺遗址公园一份）。
- 运算：分别对两园区路网做 Buffer，输出要素类 `Park_Road_Buffer`。
- 建议字段：`park_id`（如 `daxingshan` / `cien`）、`park_name`、`buffer_radius_m`、`source_road_class`（可选，便于追溯）。
- 两园区结果可合并为一个要素类，也可分两个要素类；推荐一个要素类加 `park_id` 字段，便于前端一次加载。



### 3.2 缓冲区半径确定

缓冲区半径建议作为**可配置参数**维护，不写死在模型或前端代码中，配置表建议为 `Park_Buffer_Config(park_id, buffer_radius_m, effective_date)`。

**默认值：50 米**

### 3.3 判定逻辑实现层级

**推荐 v1：前端本地判定。**

前端在进入拍照机位路线 / 季节主题路线界面时：

1. 加载两园区缓冲区数据（建议导出为 GeoJSON，可做 1~2 米容差的简化以控制体积，两个园区合计通常在几十 KB 量级）。
2. 获取定位坐标。
3. 本地做 point-in-polygon 判断，得到 `park_id` 或 `null`。

理由：

- 判定逻辑简单（点与多边形关系），本地即时完成，无额外网络往返，首屏响应更好。
- 缓冲区数据量小、变更低频，随前端配置发布或通过轻量配置接口拉取即可。
- 定位数据无需上送服务器即可完成判定，降低隐私顾虑。

备选方案（后端轻量查询接口）：`POST /api/park/locate`，入参 `{lng, lat}`，返回 `{park_id | null}`。优点是判定逻辑集中维护、不随前端发版；缺点是每次进入界面多一次网络调用，且引入服务依赖。

建议：v1 采用前端本地判定，同时在前端把判定封装为一个可替换的 `locatePark(lng, lat)` 抽象；若未来判定规则复杂化（多园区、分级缓冲、动态半径）或需要统一审计，再平滑迁移到后端轻量接口。文档中约定前后端接口层为 `park-locate`，本 GP 服务不承载该能力。

### 3.4 未落入任一园区缓冲区的兜底逻辑

游客进入拍照机位路线 / 季节主题路线界面，若定位未落在任一园区路网缓冲区内：

- 前端提示“请先到达园区范围内查看推荐路线”（文案以业务确认为准）。
- 不加载任何园区的机位点 / 观赏窗口数据。
- 不发起 GP 路径规划请求。

该兜底逻辑完全发生在前端，GP 服务不感知，也不会收到无效园区参数。

### 3.5 场景一（导航到问题树）的特殊性

- 工单关联树木的坐标是固定终点，树木所属园区直接决定使用哪个网络数据集，因此场景一不依赖缓冲区判定。
- 起点是巡检 / 养护人员实时定位，允许落在园区路网缓冲区内或园区外；人员从园区外赶来复核/处置是正常业务场景。
- 工单数据建议携带稳定的 `park_id` 字段，避免用树坐标二次推导园区。
- 若树木坐标位于路网外（如新植树木未测绘、坐标漂移），模型按吸附容差找最近路网位置；无法吸附时返回明确错误，由业务侧人工处理（列入待确认清单）。

## 四、模型输入参数设计

### 4.1 服务形态：一个通用 GP 工具，发布为一个 GP 服务

工具建议命名为 `ParkRoutePlanning`，通过 `park` 与 `scenario` 参数区分业务场景。理由：

- 三个场景核心求解完全一致：同一园区网络数据集、同一 Route 求解器、同样的输出结构；差异仅为“是否有途经点、途经点来源、是否自动排序”。
- 单一模型减少维护成本：ND 配置、坐标系、输出字段、错误处理只维护一份。
- 前端接口收敛为同一端点，联调与版本管理更简单。
- 场景差异由参数化控制：`scenario` 仅用于参数校验、日志与可选默认值，模型主干不分叉。


### 4.2 起点 / 终点坐标传入格式

**前端传 EPSG:4490 经纬度（经度 x、纬度 y），坐标转换发生在模型内部，坐标源纠偏发生在前端。**

约定：

- 前端所有定位与业务点坐标统一为 CGCS2000 经纬度（EPSG:4490）后传给 GP 服务。
- 前端负责坐标系来源纠偏：若来自浏览器 GPS（WGS84），与 CGCS2000 的差异在实用精度内可近似忽略。
- GP 服务假设入参已是 EPSG:4490，不处理 GCJ-02 偏移；模型内部将经纬度投影为 CGCS2000 3 Degree GK CM 108E（EPSG:4532，）后执行网络分析。
- 坐标传 6 位以上小数；参数类型建议使用点要素（Feature Set），单点与多点统一。

### 4.3 途经点传入方式

**推荐使用 Feature Set（要素集）参数 `stops`，允许为空。**

每个途经点为一个点要素，属性中携带前端标识：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `stop_id` | String | 是 | 前端唯一标识，用于结果顺序一一对应 |
| `stop_name` | String | 否 | 展示名称，如机位名 |
| `stop_type` | String | 否 | `photo_spot` / `view_window` / `tree` / `destination` |
| `park_id` | String | 否 | 冗余园区标识，可用于校验 |

REST 请求中 Feature Set 的逻辑结构示例：

```json
{
  "spatialReference": { "wkid": 4490 },
  "features": [
    {
      "geometry": { "x": 108.95231, "y": 34.22817 },
      "attributes": {
        "stop_id": "P1",
        "stop_name": "银杏机位",
        "stop_type": "photo_spot"
      }
    }
  ]
}
```

说明：

- ModelBuilder 中工具参数类型设置为 Feature Set，天然支持 0..N 个点要素；无途经点时传入空要素集即可。
- 备选方案为多值字符串（如 `stop_id,x,y;stop_id,x,y`）在模型内解析，但会丢失结构化属性且需要额外解析步骤，不推荐作为主方案。
- 场景一无途经点，`stops` 传空；场景二可空；场景三由模型内部按观赏窗口查询生成，前端不需要传途经点。

### 4.4 园区参数传入方式

- 参数名：`park`，GPString，必填。
- 枚举值：`daxingshan`（大兴善寺）、`cien`（唐大慈恩寺遗址公园）。建议使用稳定英文标识，避免中文、空格与大小写歧义。
- GP 服务职责：仅校验参数值是否在枚举范围内，并根据该值选择对应网络数据集；**不在模型内做缓冲区判定、不做园区推荐**。
- 模型内通过配置表 `Park_ND_Config(park_id, network_dataset_path, park_name)` 维护园区到网络数据集的映射，新增园区时改表即可，不改模型。

职责划分明确：`park` 参数是“上游已判定完成”的结果输入，GP 服务只消费它，不重复推导。

### 4.5 季节主题路线“观赏窗口”标识

- 参数名：`viewing_window_id`，GPString；仅 `scenario=season_route` 时必填，其余场景忽略。
- 预设途经点组合独立维护在数据表中，建议表结构：

```text
Viewing_Window_Stops(
  window_id      VARCHAR,   -- 观赏窗口标识，如 autumn_maple
  window_name    VARCHAR,   -- 观赏窗口名称
  park_id        VARCHAR,   -- 所属园区
  stop_id        VARCHAR,   -- 途经点标识，全局唯一建议加窗口前缀
  stop_name      VARCHAR,   -- 展示名称
  stop_type      VARCHAR,   -- photo_spot / destination
  x              DOUBLE,    -- CGCS2000 经度
  y              DOUBLE,    -- CGCS2000 纬度
  display_order  INTEGER    -- 预设/展示顺序，作前端展示与维护参考
)
```

- 模型根据 `viewing_window_id` 查询该表，将全部途经点与终点读入生成分析停靠点。
- `display_order` 用于运营维护与前端展示，**不参与求解器顺序**；实际经过顺序统一由“查找最佳顺序”计算。
- 未来运营人员调整观赏窗口仅需改表；若表在 FileGDB 内且被 GP 服务读取，需确认 GeoScene Server 的数据同步策略（服务是否随数据更新自动刷新，见待确认清单）。

### 4.6 模型输入参数总表

| 参数 | GP 类型 | 必填 | 适用场景 | 说明 |
| --- | --- | --- | --- | --- |
| `park` | GPString | 是 | 全部 | `daxingshan` / `cien`，上游判定结果 |
| `scenario` | GPString | 是 | 全部 | `tree_task` / `photo_route` / `season_route`，用于校验与日志 |
| `origin` | Feature Set（单点） | 是 | 全部 | 起点，EPSG:4490 经纬度 |
| `destination` | Feature Set（单点） | 是 | 全部 | 终点，EPSG:4490 经纬度 |
| `stops` | Feature Set（多点） | 否 | 场景二 | 可选途经点，可空 |
| `viewing_window_id` | GPString | 条件必填 | 场景三 | 观赏窗口标识，模型内查表展开途经点 |
| `snap_tolerance_m` | GPDouble | 否 | 全部 | 起终点吸附容差，默认 50 |

## 五、模型内部处理逻辑设计

### 5.1 网络数据集选择逻辑

推荐“ModelBuilder 壳 + 内嵌 Python 脚本步骤”的混合方式：

1. 模型暴露统一参数（见 4.6），提供标准 GP 服务接口形态。
2. 内部 Python 脚本读取 `park` 参数，查询 `Park_ND_Config` 映射表获得该园区的网络数据集路径。
3. 脚本内使用等价于 `Make Route Analysis Layer` + `Add Locations` + `Solve` 的流程完成求解，避免在 ModelBuilder 里为每个园区复制一套分支。

若必须使用纯 ModelBuilder 可视化实现，可用“If 参数等于”分支分别连接两套 Route 求解节点；该方式在园区数固定且需要图形化审阅时可用，但后续新增园区、改参数配置时维护成本更高，不推荐作为长期方案。

两园区网络数据集物理独立、互不连通（列入待确认，当前按此设计）：路径求解严格限定在 `park` 对应 ND 内，不存在跨园区路径，也不需要跨园区连通逻辑。

### 5.2 途经点顺序优化处理

Route 求解器关键设置：

| 设置项 | 取值 | 说明 |
| --- | --- | --- |
| 重新排序停靠点以查找最佳路径 | `FIND_BEST_ORDER`（查找最佳顺序） | 对停靠点执行 TSP 式自动排序 |
| 保留第一个停靠点 | `True` | 起点固定为路径第一点 |
| 保留最后一个停靠点 | `True` | 终点固定为路径最后一点，仅中间途经点自动排序 |

ModelBuilder / 脚本中通过 Route 分析图层属性或在 `Solve` 前设置上述参数。若业务最终确认终点也参与排序，则关闭“保留最后一个停靠点”，但需要前端明确“终点”展示语义。

**实际经过顺序的获取：**

- 求解完成后，停靠点结果要素类的 `StopSequence` 字段保存实际顺序编号（从 1 开始）。
- 模型将输入 `stop_id` 属性与 `StopSequence` 合并输出为排序表 `OrderedStops`，保证前端传入的每个 `stop_id` 都能映射到实际顺序。
- 输出结构：`stop_id`、`sequence`、`stop_name`、`is_origin` / `is_destination`；无途经点时仅起点与终点两行。

### 5.3 坐标系转换环节

转换链路：

```text
输入 EPSG:4490 经纬度点
  → Project 为 CGCS2000 3 Degree GK CM 108E（EPSG:4532，与 ND 数据定义一致）
  → 在 ND 投影坐标系下执行 Route 求解
  → 结果要素通过模型环境输出坐标系设置转回 EPSG:4490
```

实现要点：

- 模型内部先对输入 Feature Set 做投影，再作为停靠点加载到网络分析图层；不依赖前端做投影。
- 网络分析天然在 ND 自身坐标系下进行，保证与路网几何一致。
- 模型环境（Environment）中统一设置“输出坐标系 = EPSG:4490”，使输出路径要素和停靠点结果几何均为经纬度，直接兼容天地图。
- 起终点吸附：`Add Locations` 时设置寻路容差 `snap_tolerance_m`，默认 50 米；超出容差且无法吸附时返回 `LOCATION_NOT_ON_NETWORK` 错误。
- 最终发布前需在桌面端验证：输入 4490 坐标、输出结果 spatialReference 为 4490、路径几何正确贴合路网。

## 六、模型输出结果设计

### 6.1 输出内容与字段

| 输出 | 类型 | 关键字段 | 说明 |
| --- | --- | --- | --- |
| 路径几何 | Polyline 要素类 | `Shape` | EPSG:4490 经纬度折线，供天地图叠加 |
| 总距离 | Double | `total_meters` | 网络求解得到的步行距离，单位：米 |
| 预计时间 | Double | `estimated_minutes` | 模型内计算，单位：分钟 |
| 途经点实际顺序 | 表 / 要素集 | `stop_id`、`sequence` | 与前端传入标识一一对应 |
| 结果状态 | 表 / JSON | `status`、`message` | 成功、失败原因、警告等 |

字段命名建议统一采用小写下划线风格，最终以接口契约为准。

### 6.2 途经点实际顺序输出

输出 `OrderedStops` 示例：

| stop_id | sequence | stop_name | is_origin | is_destination |
| --- | --- | --- | --- | --- |
| `origin` | 1 | 我的位置 | true | false |
| `P2` | 2 | 石狮机位 | false | false |
| `P1` | 3 | 银杏机位 | false | false |
| `dest` | 4 | 大雁塔北广场 | false | true |

前端可根据 `stop_id` 将实际顺序与原始选项对应，不受前端传参顺序影响。

### 6.3 步行时间计算方式

- 网络数据集阻抗建议使用**距离（米）**，路径优化目标为最短步行距离。
- 步行速度固定为 **4.8 km/h**，不作为 GP 输入参数，前端不传、用户不可调整。
- 预计步行时间在模型内按固定速度计算：`estimated_minutes = total_meters / (4.8 * 1000 / 60)`。
- 如需调整速度，由后端在模型/配置中修改固定值后重新发布服务，前端无需感知。
- 说明：该时间是对网络距离的线性估算，不模拟等待、上下坡、红绿灯等；若业务要求更精细，可在 ND 中增加步行时间成本属性，但速度会固化在 ND 中，调整需重建 ND，当前方案调整成本更低。

### 6.4 输出坐标系确认

- 模型环境“输出坐标系”统一配置为 EPSG:4490。
- 输出路径、停靠点、排序表几何均为 4490 经纬度。
- 发布服务后建议用已知起终点做回归验证，确认前端拿到的 geometry 直接可用于天地图坐标。

## 七、与前端的接口约定

### 7.1 请求方式：异步提交任务（submitJob）

理由：

- 网络分析耗时与网络规模、途经点数量相关，通常秒级，复杂请求可能更长；同步 execute 容易触发 HTTP 网关或服务超时。
- 异步方式天然支持排队、进度查询、超大结果分页拉取，适合移动端弱网环境。
- GeoScene Server 对 GP 服务原生支持 submitJob / jobStatus / results 轮询模式。

前端流程：`submitJob` → 轮询 `jobStatus`（显示加载态）→ 完成后按结果参数名拉取路径、排序表、状态。

### 7.2 请求参数结构

实际调用 GP REST 时以表单字段提交，字段值为 Feature Set JSON 或字符串；逻辑结构如下：

```json
{
  "park": "daxingshan",
  "scenario": "photo_route",
  "origin": {
    "spatialReference": { "wkid": 4490 },
    "features": [
      { "geometry": { "x": 108.95123, "y": 34.22123 }, "attributes": { "stop_id": "origin" } }
    ]
  },
  "destination": {
    "spatialReference": { "wkid": 4490 },
    "features": [
      { "geometry": { "x": 108.96111, "y": 34.23222 }, "attributes": { "stop_id": "dest" } }
    ]
  },
  "stops": {
    "spatialReference": { "wkid": 4490 },
    "features": [
      { "geometry": { "x": 108.95231, "y": 34.22817 }, "attributes": { "stop_id": "P1", "stop_name": "银杏机位" } },
      { "geometry": { "x": 108.95577, "y": 34.22551 }, "attributes": { "stop_id": "P2", "stop_name": "石狮机位" } }
    ]
  },
  "viewing_window_id": "",
  "snap_tolerance_m": "50",
  "env:outSR": "4490"
}
```

说明：

- `scenario` 与 `park` 必须同时正确；`season_route` 时 `viewing_window_id` 必填。
- 场景一不传 `stops`；场景二不选途经点时传空 Feature Set；场景三前端不传 `stops` 与终点，由后端预设提供。
- 请求不包含步行速度参数，模型按固定 4.8 km/h 计算预计时间。
- 请求统一带 `env:outSR=4490`，服务端输出坐标系双保险。

### 7.3 返回结果结构

异步任务完成后，前端从结果中组装如下逻辑结构：

```json
{
  "status": "success",
  "route": {
    "geometry": {
      "type": "LineString",
      "coordinates": [
        [108.95123, 34.22123],
        [108.95231, 34.22817],
        [108.95577, 34.22551],
        [108.96111, 34.23222]
      ]
    },
    "total_meters": 1234.5,
    "estimated_minutes": 15.4
  },
  "stop_order": [
    { "stop_id": "origin", "sequence": 1, "is_origin": true, "is_destination": false },
    { "stop_id": "P2", "sequence": 2, "is_origin": false, "is_destination": false },
    { "stop_id": "P1", "sequence": 3, "is_origin": false, "is_destination": false },
    { "stop_id": "dest", "sequence": 4, "is_origin": false, "is_destination": true }
  ],
  "messages": []
}
```

错误码约定：

| 错误码 | 含义 |
| --- | --- |
| `INVALID_PARK` | 园区参数不合法 |
| `INVALID_SCENARIO` | 场景参数不合法 |
| `MISSING_VIEWING_WINDOW` | 季节主题路线缺少观赏窗口标识 |
| `NO_ROUTE` | 起终点不可达（网络不连通） |
| `LOCATION_NOT_ON_NETWORK` | 起终点/途经点超出吸附容差，无法定位到路网 |
| `SERVICE_ERROR` | 服务内部异常 |

### 7.4 前后端职责分界（接口层重申）

- **前端或前端调用的轻量业务接口负责**：定位获取与坐标纠偏、园区路网缓冲区判定、机位点 / 观赏窗口的园区归属过滤、向 GP 服务传入已确定的 `park`。
- **GP 服务负责**：仅接受“已知园区标识 + 起点 + 终点 + 可选途经点（或观赏窗口标识）”，完成纯路径计算、顺序优化、坐标转换与结果输出。
- 后端负责人不要为 GP 模型增加“定位是否在园区内”“返回该园区机位点列表”等能力；若业务需要服务端园区判定，应单独实现轻量查询接口，与本 GP 服务解耦。

## 九、已确认清单

1. **缓冲区半径取值**： 50 米，可两园区分别配置；需业务确认实际体验（误判率、机位点分布、出入口距离）。
2. **缓冲区生成方式**：离线预生成（与 ND 构建同阶段）；确认可接受路网变更时人工重跑数据准备流程。
3. **判定逻辑层级**： v1 前端本地判定；确认前端可随配置发布 / 更新缓冲区 GeoJSON，否则改走后端轻量接口。
4. **两园区路网物理独立互不连通**：确认按此设计，不做跨园区路径
5. **自动排序范围**：确认“起点固定第一、终点固定最后、仅中间途经点自动排序”；若终点也参与 TSP 需明确前端语义。
6. **定位坐标系来源与纠偏责任**：确认前端定位来源（浏览器 GPS / 高德 / 腾讯）及 GCJ-02 纠偏由前端完成，GP 服务只接收 EPSG:4490。
7. **投影 EPSG 精确值**：确认路网实际为 CGCS2000 3 Degree GK CM 108E（EPSG:4532）还是带带号分带版本，模型投影参数必须与数据完全一致。
8. ~~步行速度默认值~~：已确认固定为 4.8 km/h，不作为用户输入参数，不再需要业务确认。
9. **吸附容差**： 50 米；确认起终点在路网外时的处理口径。
10. **观赏窗口预设数据维护位置与更新机制**：确认表放 FileGDB 还是业务数据库、运营如何更新、GeoScene Server 数据同步策略。
12. **未到达园区提示文案**：确认“请先到达园区范围内查看推荐路线”文案，以及是否需要“最近园区 + 距离”提示。
13. **结果字段与单位**：确认 `total_meters` / `estimated_minutes` / `stop_id` 字段命名及米 / 分钟单位，保证前后端契约一致。
15. **性能与超时预期**：确认并发量、可接受耗时，用于决定异步轮询间隔与 GeoScene Server 资源规划。
